## 1. 배경 — 청킹은 RAG의 숨은 병목

RAG(Retrieval-Augmented Generation)는 외부 지식 기반에서 관련 정보를 검색하고, 이를 맥락으로 삼아 LLM이 답변을 생성하는 두 단계로 이루어진다.

**문제**: 현재의 청킹 방식들은 종종 임의의 경계를 강제하면서 맥락적 연결을 끊어버린다.

> 논문은 이를 **"맥락 보존 딜레마(context-preservation dilemma)"** 라고 부른다.

하나의 완결된 정보가 여러 청크로 흩어지면, 검색 단계에서 그 정보를 온전히 길어올리지 못해 답변 품질이 떨어진다.

**예시**: 질의가 대명사를 포함하는데, 그 대명사가 가리키는 대상이 다른 청크에 있다면 → 검색된 맥락만으로는 답을 구성할 수 없다.

## 2. 기존 청킹 방식과 한계

| 방식 | 설명 | 한계 |
|------|------|------|
| **문장 기반 분할** | 고정 개수의 문장으로 분리 | 단락 같은 더 큰 논리 블록을 자주 끊음 |
| **재귀적 분할** (LangChain RecursiveCharacterTextSplitter) | 구분자 계층을 순서대로 적용, 길이 제약 맞춤 | 서로 무관한 주제를 한 청크에 묶어 응집성 저하 |
| **의미 기반 청킹** | 임베딩으로 의미적 경계에서 분리 | 응집성은 좋으나 반복 임베딩 계산으로 연산 비용 매우 큼 |
| **LLM 기반 분할** | 언어 모델로 자연스러운 경계 추론 | 완결성은 높으나 전체 코퍼스에 단일 전략 가정, 오버헤드 큼 |

**공통 한계**: 문서의 구조적·맥락적 차이를 무시하고 모든 문서에 하나의 고정 전략을 적용한다.

## 3. 핵심 아이디어 — 평가 지표를 먼저 만들자

### 기존 문제`

청킹 품질을 Hits@k, Recall@K, nDCG@K 같은 다운스트림 검색 지표로 **간접** 측정해왔다.
→ 청킹 자체의 효과를 다른 요인과 분리해 평가하기 어렵다.

### 발상의 전환

순서를 뒤집는다. **청크 품질을 직접 측정하는 내재적 지표(intrinsic metrics)를 먼저 설계**하고, 그 지표로 문서별 최적 방법을 자동 선택한다.

### 이상적인 청크의 4가지 속성

1. **자기 완결성** — 홀로 읽어도 이해된다
2. **적정 길이** — 임베딩 모델의 토큰 한계를 존중한다
3. **의미적 응집성** — 하나의 주제에 집중한다
4. **맥락 보존** — 문서의 자연스러운 구조와 정렬된다

### 논문의 3가지 기여

1. 청크 품질을 직접 재는 **5가지 내재적 지표**
2. **LLM 정규식 분할기**와 **분할 후 병합 재귀 분할기** 2가지 새로운 청킹 기법
3. 검색 품질과 다운스트림 RAG 성능을 함께 측정하는 **평가 파이프라인**

## 4. 5가지 내재적 지표

> 모든 지표는 **정답(ground-truth) 없이** 계산된다. 별도 라벨링 작업 없이 청크 자체만으로 품질 판단.

### RC — References Completeness (참조 완결성)

**측정 내용**: 개체-대명사 쌍이 같은 청크 안에 온전히 존재하는 비율

- Maverick 상호참조 해소 모델로 멘션 클러스터 추출
- 개체와 대명사 사이에 청크 경계가 끼어들면 페널티
- **제약**: Maverick이 영어만 지원 → 영어 문서에만 적용 가능

```
RC = 1 - (청크 경계로 분리된 개체-대명사 쌍 수) / (전체 쌍 수)
```

---

### BI — Block Integrity (블록 무결성)

**측정 내용**: 문단·표·그림·제목-본문 쌍 같은 구조적 단위가 깨지지 않고 보존되는 비율

- 파서가 제공한 블록 경계 기준
- 오탐 방지를 위해 **τ = 5 글자** 허용 오차 적용
- 표가 두 청크로 쪼개지면 사실상 쓸모없어짐

---

### ICC — Intrachunk Cohesion (청크 내부 응집성)

**측정 내용**: 한 청크 안에서 문장들이 얼마나 같은 주제를 향하는지

- 문장 임베딩과 청크 전체 임베딩 사이의 **평균 코사인 유사도**
- 임베딩 모델: `jina-embeddings-v3` (Jina AI)
- ICC가 높은 청크 = 내부적으로 한 주제에 집중 = 검색 신호가 선명

---

### DCC — Document Contextual Coherence (문서 맥락 일관성)

**측정 내용**: 각 청크가 주변의 더 넓은 지역적 맥락과 얼마나 잘 정렬되는지

- ICC가 청크 **내부**를 본다면, DCC는 청크와 **주변의 관계**를 본다
- 최대 **3,000 토큰 슬라이딩 윈도우** 구성
- 청크가 홀로도 이해되면서 동시에 문서 수준 맥락을 잃지 않았는지 확인

> **ICC vs DCC 상충 관계**
> - 청크가 작을수록 → ICC ↑, DCC ↓
> - 청크가 클수록 → DCC ↑, ICC ↓

---

### SC — Size Compliance (크기 준수)

**측정 내용**: 토큰 길이가 사전 정의 범위 안에 드는 청크의 비율

- 실험 기준: **100 ~ 1,100 토큰**
- 너무 큰 청크 → 하나의 임베딩에 여러 개념이 섞여 의미 희석
- 너무 작은 청크 → 정보 빈약, 검색 슬롯 낭비

---

### 5가지 지표 요약

| 지표 | 측정 대상 | 핵심 실패 모드 방지 |
|------|-----------|---------------------|
| RC | 대명사-개체 참조 완결성 | 대명사가 다른 청크에 분리되는 문제 |
| BI | 구조 블록 무결성 | 표·그림이 두 청크로 쪼개지는 문제 |
| ICC | 청크 내부 주제 응집성 | 서로 다른 주제가 한 청크에 섞이는 문제 |
| DCC | 문서 맥락과의 일관성 | 청크가 주변 맥락과 단절되는 문제 |
| SC | 토큰 크기 준수 | 너무 크거나 너무 작은 청크 문제 |

## 5. 두 가지 새로운 청커

### LLM Regex Splitter

LLM의 구조 분석 능력 + 정규식의 결정론적 특성을 결합.

**동작 방식**
1. LLM에게 청킹 가이드라인 + 문서 앞부분(8,000 토큰) 샘플 제공
2. LLM이 해당 문서에 적합한 **정규식 패턴 하나** 생성
3. `re.split`으로 문서 전체에 적용

**장점**
- LLM을 모든 경계마다 호출하지 않고 패턴 하나만 추출 → 빠름
- 법률 문서, 조항 구분자처럼 명확한 패턴이 있는 구조화 텍스트에 효과적

---

### Split-then-Merge Recursive Splitter

LangChain 재귀 분할기에서 영감, 두 번의 패스(two-pass)로 동작.

**1차 패스**: 구분자 우선순위(제목 → 섹션 → 문장 → 글자)로 재귀 분할
→ 각 조각이 크기 S 이하가 될 때까지

**2차 패스**: 인접 조각들을 S를 넘지 않는 선에서 탐욕적으로 병합
→ 필요시 백트래킹, 오버랩 유지, 너무 커진 부분은 재분할

**실험 변형**: 목표 크기 1,100 토큰 버전 / 600 토큰 버전 두 가지

---

## 6. 후처리: 크기 정규화

두 청커 모두 마지막 정규화 단계를 거친다.

| 처리 | 기준 | 방법 |
|------|------|------|
| **과대 청크 분할** | > 1,100 토큰 | 동일한 구분자 계층으로 재분할 |
| **과소 청크 병합** | < 100 토큰 | 인접 조각과 합침 (합친 크기 ≤ 1,150 토큰) |

**효과**: SC와 평균 내재적 점수를 방법에 따라 **6 ~ 16pp** 향상
- LLM 정규식: SC 58.3% → **99.6%**
- 의미 기반 청커: SC 48.1% → **99.9%**

## 7. 실험 설계

### 하이브리드 검색 파이프라인 (청킹 외 변수 고정)

```
사용자 질의
    ↓ Qwen3-Embedding-4B 임베딩
    ├── BM25 어휘 검색 → 상위 50개
    └── 의미 검색 → 상위 50개
    ↓ 중복 제거 (100개 후보)
    ↓ snowflake-arctic-embed-l-v2.0 리랭커 → 상위 10개
    ↓ GPT-4.1 (temperature=0) 답변 생성
```

### 실험 코퍼스

- **33개 실제 PDF 문서** (Ekimetrics CLAIR 프로젝트)
- 도메인: 법률, 기술, 사회과학
- 총 약 **118만 토큰**
- 문서당 평균 토큰: 기술 5,257 / 법률 30,895 / 사회과학 79,862

### 평가 지표

| 지표 | 설명 | 측정 방법 |
|------|------|-----------|
| **Retrieval Completeness** | 검색된 맥락이 정답을 얼마나 잘 뒷받침하는지 | GPT-4.1 심판 (0·1·2점 → 0~1 정규화) |
| **Answer Correctness** | 생성된 답변과 정답의 사실 정합성 | G-Eval (0~1 척도) |

## 8. 실험 결과

### 청킹 품질 비교 (내재적 지표)

| 방법 | RC | ICC | DCC | BI | SC | **평균** |
|------|-----|-----|-----|-----|-----|---------|
| **Adaptive Chunking** | 99.0 | 68.2 | 88.8 | 99.4 | 99.9 | **91.07** |
| LLM Regex (GPT) | 98.0 | 70.9 | 82.4 | 98.1 | 99.6 | 89.80 |
| LangChain Recursive | 96.1 | 65.6 | 88.8 | 95.0 | 97.7 | 88.62 |
| Semantic | 97.5 | 69.3 | 76.3 | 91.3 | 48.1 | 76.49 |
| Sentence | 86.3 | 78.4 | 72.5 | 61.9 | 67.2 | 73.26 |

> 문장 기반 청킹이 ICC에서 78.4로 가장 높음 — 작은 단위 덕에 주제 혼합이 적기 때문.
> 어떤 단일 방법도 모든 지표에서 1등이 아님 → 문서별 선택 정책이 필요한 이유.

### 지표 간 상관관계

- 스피어만 상관계수 범위: **-0.44 < ρ < 0.31** (약하거나 중간 수준)
- 5개 지표가 서로 **보완적인 현상**을 포착함을 의미

**두 가지 핵심 상충 관계**

| 상충 | 원인 |
|------|------|
| ICC ↑ ↔ DCC ↓ | 청크가 작을수록 내부 응집성은 높지만 주변 맥락 신호를 잃음 |
| ICC ↑ ↔ BI ↓ | 구조 단위를 온전히 유지하면 이질적 요소가 한 청크에 들어가 응집성 저하 |

### Adaptive 정책의 실제 선택 분포

| 청커 | 선택 비율 | 적합한 문서 유형 |
|------|-----------|-----------------|
| 페이지 청킹 | 48% | 표·각주·페이지 정렬 조항이 많은 문서 |
| Recursive (s=1100) | 42% | 길게 이어지는 서술형·위계적 문서 |
| LLM Regex | 6% | 명확한 패턴 구분자가 있는 문서 |
| Recursive (s=600) | 3% | 세밀한 청킹이 필요한 문서 |

### RAG 성능 비교

| 지표 | **Adaptive** | LC 재귀 (기본) | 페이지 (원본) |
|------|-------------|---------------|--------------|
| Retrieval Completeness | **67.68%** | 58.08% | 59.09% |
| Answer Correctness | **78.01%** | 70.11% | 73.33% |
| 종합 평균 | **71.77%** | 62.07% | 63.80% |
| 답변한 질문 수 | **65 / 99** | 49 / 99 | 49 / 99 |

**향상폭**
- Retrieval Completeness: LangChain 대비 **+9.60pp (+16.5%)**
- 답변 가능 질문 수: **+16개 (+32.7%)**

### 증폭 효과

> 내재적 지표 차이 **0.4 ~ 2.4pp** → RAG 성능 차이 **8 ~ 10pp**로 증폭

청크 품질의 작은 개선이 검색·생성 파이프라인을 거치며 **복리처럼 누적**되기 때문.

### 런타임

| 방법 | 평균 런타임 |
|------|------------|
| LLM Regex | 146.85초 |
| Recursive 분할기 | 28 ~ 31초 |
| Adaptive 전체 파이프라인 | 약 210초 |

> 색인 시점(indexing time)에 한 번만 발생 → 서비스 질의 응답 속도에 영향 없음

## 9. 한계점 및 향후 연구

| 한계 | 내용 |
|------|------|
| **계산 효율성** | DCC(슬라이딩 윈도우 임베딩 반복)와 개체-대명사 추출이 병목 |
| **언어 범위** | RC는 Maverick 모델 제약으로 영어 문서만 지원 |
| **도메인 범위** | 형식적 문서(법률·기술·사회과학) 위주, 비형식 텍스트·멀티모달 미검증 |
| **하이퍼파라미터** | 청크 크기(100~1,100), 윈도우(3,000), 지표 가중치가 경험적 설정 |
| **질의 비적응성** | 청킹 전략이 색인 시점에 고정, 질의 특성에 맞춰 동적 변경 불가 |

## 10. 결론 및 실무 제언

### 핵심 메시지

> 더 큰 모델과 더 긴 컨텍스트만이 답이 아니다.
> 문서를 구조에 맞춰 정성껏 자르는 것만으로도 RAG를 더 견고하게 만들 수 있다.

### 3가지 실무 제언

1. **전역 기본값보다 문서 인식 선택을 우선하라**
   단일 청커가 평균 점수에서 가장 좋더라도, 문서별 선택이 더 높은 검색 완전성과 답변율을 가져온다.

2. **항상 크기를 정규화하라**
   과소 청크 병합과 과대 청크 재분할은 미미한 비용으로 일관된 이득을 준다.

3. **응집성과 맥락의 균형을 잡으라**
   하나의 차원만 최적화하지 말고 5지표를 함께 보는 다중 지표 점수를 사용하라.
