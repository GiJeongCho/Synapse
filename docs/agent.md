## 에이전트를 만드는 에이전트 

MCP 도구를 추가해서 이용하는 개념을 사용하고자 해.

A. 핵심 컴포넌트
Requirements Analyzer (요구사항 분석기): 사용자의 목적을 분석하여 하위 에이전트의 페르소나, 목표, 제약사항을 정의합니다.

Tool & Context Retriever (도구 검색기): 하위 에이전트에게 필요한 MCP 서버나 API를 탐색합니다. 이때 사용 가능한 수많은 MCP 도구들의 명세(Schema)를 관리하고 검색하기 위해 Knowledge Graph(예: Neo4j)나 Vector DB를 활용하는 RAG 파이프라인을 구축하는 것이 효과적입니다.

Environment Provisioner (환경 프로비저닝): 생성된 하위 에이전트가 독립적으로 실행될 수 있는 환경을 구성합니다. 빠르고 가벼운 패키지 관리를 위해 uv를 사용하여 의존성을 정의하고, Docker를 통해 컨테이너화된 실행 환경(Dockerfile)을 자동 생성하도록 구성하면 실무 배포가 매우 용이해집니다.

Evaluator (평가기): 생성된 에이전트가 주어진 도구를 제대로 호출하는지 샌드박스 환경에서 테스트하고, 실패 시 프롬프트나 부여된 MCP 구성을 수정(Self-Correction)합니다.

B. 파이프라인 흐름
Input: "최신 환율 정보를 바탕으로 무역 차익을 계산하는 에이전트를 만들어줘."

Plan: Meta-Agent가 시스템 프롬프트 초안 작성.

Retrieve: 도구 저장소(KG/Vector DB)에서 Exchange-Rate-MCP 및 Calculator-MCP 명세서 검색 및 선택.

Build: 시스템 프롬프트 + 선택된 MCP 서버 URI 목록 + uv 기반의 pyproject.toml 생성.

Test: 더미 입력을 주고 도구 호출(Tool Call) 성공 여부 검증.

Deploy: Docker 이미지로 빌드 및 실행.

##### 요구사항 분석기를 만들기 전에 
어떤 에이전트를 실행할지 평가하는 

** 참고 : 에이전트가 3번 실패시 그냥 거기서 끝내고 오류를 반환해야 함. 즉 다음 단계로 넘어가지 못하면 안됨
** 가운데서 처리하는 평가자 에이전트(오케스트레이션1)는 값싼 토큰을 사용하고 잘 되는 보아야 함. 

** 문제 : 어떻게 에이전트를 다 만들었다고 평가할 오케스트레이션2.도 필요할 것으로 보임. 오케스트레이션2는 오케스트레이션 1을 수정할 수도 있음.
오케스트레이션 2도 상황에 따라 오케스트레이션 1을 수정할 수도 있게 하면 해결 될 것으로 보임. 

메타 에이전트: 요구사항을 분석하여 특정 작업을 수행할 노드(Child Agent)들을 동적으로 생성합니다.

MCP: 각 노드(Agent)가 외부 인프라 및 데이터와 소통할 수 있도록, 도구(Tool/Context)를 표준화된 규격으로 연결해 줍니다.

오케스트레이션: 생성된 노드와 도구들을 그래프 형태로 엮어, "A 에이전트가 MCP로 외부 데이터를 가져오면 -> B 에이전트가 분석하고 -> 평가를 거쳐 통과하면 종료" 하는 식의 전체 실행 궤도를 통제합니다.
