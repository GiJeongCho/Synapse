## 모듈별 상세 설명

### `backend/app/main.py`

FastAPI 애플리케이션 진입점. CORS 미들웨어를 설정하고, `documents`와 `search` 라우터를 마운트한다. `/health` 헬스체크 엔드포인트를 포함.

### `backend/app/config.py`

`pydantic-settings` 기반 전역 설정 관리. `.env` 파일에서 환경 변수를 읽어온다.

| 설정 그룹 | 주요 항목 |
|-----------|-----------|
| LLM | `anthropic_api_key`, `llm_model` (claude-sonnet) |
| 임베딩 | `embedding_model` (all-MiniLM-L6-v2), `embedding_dim` (384) |
| Milvus | `milvus_uri` (로컬 synapse.db), `milvus_collection` |
| 청크 크기 | `chunk_min_tokens` (100), `chunk_max_tokens` (1100) |
| 스코어링 | `quality_weight` (0.4), `importance_weight` (0.6) |
| Neo4j | `neo4j_uri`, `neo4j_user`, `neo4j_password` |

---

### `backend/app/preprocessing/` — 전처리 파이프라인

Adaptive Chunking 논문(LREC 2026)을 구현한 핵심 모듈.

#### `classifier.py` — 문서 타입 분류

입력 텍스트를 `paper` / `news` / `law` 중 하나로 분류한다.

- **1차**: 정규식 휴리스틱 (arXiv ID, "제N조", "기자" 등 패턴 매칭)
- **2차**: 신뢰도 낮으면 Claude LLM 폴백

#### `chunkers/` — 청킹 전략 3종

| 파일 | 전략 | 적합한 문서 |
|------|------|-------------|
| `llm_regex.py` | LLM이 문서 앞부분(8K 토큰)을 보고 정규식 1개 생성 → 전체 적용 | 논문 (섹션 헤딩), 법령 (조항 구분자) |
| `split_merge.py` | 2-pass: 구분자 계층으로 재귀 분할 → 인접 조각 탐욕 병합 | 법령, 서술형 긴 문서 |
| `recursive.py` | 구분자 계층(`\n\n` → `\n` → `. ` → ` `) 재귀 분할 + 오버랩 | 뉴스, 일반 텍스트 |

#### `metrics.py` — 5가지 품질 지표

| 지표 | 측정 대상 | 계산 방식 |
|------|-----------|-----------|
| **RC** | 대명사-개체 참조 완결성 | 대명사가 선행사와 같은 청크에 있는 비율 (영어만) |
| **BI** | 구조 블록 무결성 | Markdown 제목/표/코드펜스/법령 조항이 깨지지 않은 비율 |
| **ICC** | 청크 내부 응집성 | 문장 임베딩과 청크 전체 임베딩 간 코사인 유사도 평균 |
| **DCC** | 문서 맥락 일관성 | 청크와 3,000 토큰 슬라이딩 윈도우 간 코사인 유사도 |
| **SC** | 크기 준수 | 100~1,100 토큰 범위 안에 드는 청크의 비율 |

#### `normalize.py` — 크기 정규화

- **과대 청크**(>1,100 토큰): 재귀 분할로 쪼갬
- **과소 청크**(<100 토큰): 인접 청크와 병합 (합산 ≤1,150 토큰)

#### `scoring.py` — 중요도 스코어링

논문에 없는 프로젝트 고유 기능. 4가지 신호를 결합해 `importance_score`(0~1)와 `color_intensity`(0~1)를 산출.

| 신호 | 내용 |
|------|------|
| 위치 가중치 | Abstract/Conclusion +0.3, Acknowledgement -0.5 등 |
| 키워드 밀도 | 도메인별 핵심어 빈도 (논문/법령/뉴스 각각 다른 사전) |
| 인용 밀도 | `[N]` 형태의 인용 패턴 카운트 (논문 한정) |
| LLM 분류 | "핵심 주장인가?" binary 판단 (선택적) |

최종 레이블: **Core** (≥0.7) / **Support** (≥0.4) / **Context** (≥0.15) / **Noise** (<0.15)

#### `pipeline.py` — 오케스트레이터

전처리 전체 흐름을 하나로 묶는 진입점.

```
분류 → 3종 청커 병렬 실행 → 각각 5지표 채점 → 최고점 청커 채택
→ 크기 정규화 → 중요도 스코어링 → 임베딩 → Milvus 저장
```

`reembed_and_upsert()` 함수로 HITL 수정 후 단일 청크 재임베딩도 지원.

### `backend/app/vectordb/milvus_client.py` — Vector DB

Milvus (로컬=Milvus Lite `.db` / 프로덕션=Docker 서버)와의 모든 상호작용을 담당.

| 함수 | 역할 |
|------|------|
| `ensure_collection()` | 컬렉션이 없으면 자동 생성 (384차원, string ID) |
| `embed_texts()` | sentence-transformers로 배치 임베딩 |
| `upsert_chunks()` | 벡터 + 메타데이터(source, importance, color_intensity 등) 저장/갱신 |
| `search()` | 시맨틱 유사도 검색 + 필터 |
| `delete_chunks()` | ID 기반 삭제 |
| `get_chunks_by_source()` | 특정 문서의 전체 청크 조회 |
| `list_sources()` | 저장된 문서 목록 조회 |

### `backend/app/rag/` — RAG 검색

#### `retriever.py` — 하이브리드 검색

Milvus 시맨틱 검색 결과에 `importance_score` 기반 부스팅을 적용해 후보를 정렬.

#### `reranker.py` — 리랭킹

쿼리와 각 후보 청크를 다시 임베딩해 코사인 유사도를 계산하고, 원래 점수(0.4) + 리랭크 점수(0.6) 가중합으로 최종 순위를 매김.

---

### `backend/app/graph/neo4j_client.py` — Graph DB (Phase 2)

Neo4j에 지식 그래프를 구축. 문서 유형에 따라 3가지 관계 전략 중 하나를 선택.

| 전략 | 노드 → 엣지 → 노드 | 용도 |
|------|---------------------|------|
| `word_sentence` | Keyword →[APPEARS_IN]→ Chunk | 키워드가 어느 청크에 등장하는지 |
| `sentence_sentence` | Chunk →[FOLLOWS]→ Chunk | 청크 간 순서·인접 관계 |
| `word_word` | Keyword →[CO_OCCURS]→ Keyword | 슬라이딩 윈도우 내 키워드 동시 출현 |

`build_graph_for_document()`로 문서 단위 그래프 생성, `get_document_graph()`로 시각화용 서브그래프 조회.

### `backend/app/agents/` — Multi-Agent (Phase 3)

LangGraph Supervisor 패턴으로 구성된 리서치 파이프라인.

| 파일 | 역할 |
|------|------|
| `state.py` | `ResearchState` — 에이전트 간 공유 상태 (query, search_results, analysis, report 등) |
| `tools.py` | 에이전트가 호출하는 도구 래퍼 (Milvus 검색, Neo4j 탐색) |
| `nodes.py` | 4개 에이전트 노드 구현 |
| `graph_builder.py` | StateGraph를 조립하고 조건부 라우팅 설정 |

**에이전트 흐름:**

```
Orchestrator (질문 분해, 라우팅 결정)
    ↓
Search Agent (Milvus 검색 + 리랭킹)  ──┐
Graph Agent (Neo4j 관계 탐색)         ──┤
    ↓                                    │
Analyst Agent (정보 충분성 판단) ←───────┘
    ├── 충분 → Writer Agent (리포트 생성) → 완료
    └── 부족 → Search/Graph 재호출 (최대 5회 루프)
```

### `backend/app/api/` — REST API

| 파일 | 엔드포인트 | 역할 |
|------|-----------|------|
| `documents.py` | `POST /api/documents/upload` | 파일 업로드 → 전처리 파이프라인 실행 |
| | `GET /api/documents/list` | 저장된 문서 목록 |
| | `GET /api/documents/chunks/{source}` | 문서별 청크 조회 (color_intensity 내림차순) |
| | `POST /api/documents/chunks/edit` | 청크 텍스트 수정 → 재임베딩 → upsert |
| | `POST /api/documents/chunks/delete` | 청크 삭제 |
| `search.py` | `POST /api/search/query` | RAG 검색 (시맨틱 + 리랭킹 + 필터) |

### `frontend/app.py` — Streamlit HITL 인터페이스

3개 페이지로 구성된 Streamlit 앱.

| 페이지 | 기능 |
|--------|------|
| **문서 업로드** | PDF/TXT/MD 파일 업로드 → 자동 전처리 실행 |
| **문서 뷰어** | 저장된 문서 선택 → 청크를 `color_intensity` 기반 색 농도로 표시. 연한(저점수) 청크를 텍스트 편집하거나 삭제 → 재임베딩 재저장 |
| **RAG 검색** | 자연어 질의 입력 → 시맨틱 검색 + 리랭킹 → 결과를 색 농도로 시각화 |
