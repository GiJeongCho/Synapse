> 마지막 갱신: 2026-06-29 (하네스 2종 + 도구 청소부(삭제 심판) 반영)

---

## 0. 한눈에 보는 에이전트 사용 흐름 (중요)

Meta-Agent로 만든 에이전트는 **생성 → (설정 확인) → 실행 / 스케줄 등록** 단계를 거친다.
생성만 하면 자동으로 돌지 않는다. 아래 흐름을 따라야 메일이 발송된다.

```
1) 에이전트 생성   (에이전트 생성 페이지)
   └ Meta-Agent가 실행 가능한 MCP 도구(Python 파일)를 생성·저장

2) 필수 설정 확인  (에이전트 관리 → 상세)
   └ SMTP/API 키 등 prereq 체크. ✗가 있으면 .env 채워야 함

3) 실행 방법 2가지
   ├ (A) 즉시 실행   : 에이전트 관리 → "실행" 버튼  → 도구 파이프라인 1회 실행
   └ (B) 자동 실행   : 스케줄 페이지 → cron 등록    → 주기적으로 자동 실행
```

> ⚠️ **스케줄 등록은 현재 "사람이 수동으로" 해야 한다.**
> 에이전트 생성 단계는 도구만 만들 뿐, 스케줄을 자동 등록하지 않는다.
> "매일 9시 10분", "1시간마다" 같은 표현이 요청에 있어도, 실제 cron 등록은
> 스케줄 페이지에서 직접 해야 자동 발송이 시작된다.
> (자동 등록은 향후 개선 항목 — §8 참고)

# Graph DB (선택)

NEO4J_PASSWORD=your_password

# SMTP (에이전트 메일 발송용)
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=your_id@gmail.com
SMTP_PASSWORD=앱_비밀번호_16자리   # Gmail 2단계 인증 → 앱 비밀번호

- Provisioner가 만드는 도구 코드는 **LLM 출력**이라 매번 다르다.
  환경변수명(SMTP_*)·반환 형식은 프롬프트로 강제하지만 100% 보장은 아니다.

## 5.5 도구 안정성 설계 — 같은 실패를 반복하지 않기 위한 3중 안전망 {#robustness}

과거에 반복된 실패(인자 누락 크래시, 대용량 본문 전달, 차단/키 필요 소스,
환경변수 누락 등)를 막기 위해 **생성 규칙 → 런타임 방어 → 자가개선** 3단으로 구성한다.

### (1) 생성 규칙 — Provisioner/Evaluator 프롬프트 (`agents/meta_agent/prompts.py`)

| 규칙 | 목적 |
|------|------|
| 모든 함수는 `**kwargs` + 모든 파라미터에 기본값 | "missing required argument" 크래시 방지 |
| 파이프라인 I/O 계약 고정 (`content`/`summary`/`summary_text` 등) | 도구 간 자동 연결 보장 |
| fetch/parse는 원본 HTML 금지 → `get_text()` + **15,000자 절단** | 대용량 페이로드/요약 실패 방지 |
| **다중 소스 폴백**: 후보 소스(스크래핑+RSS) 여러 개를 순서대로 시도, 첫 성공 사용 | 한 소스 차단/빈 본문 시 자동으로 다음 시도 |
| 스크래핑 **허용**(정상 UA), 단 키 필요 서비스(NewsAPI 등) 금지 | `NEWSAPI_KEY not set` 류 실패 방지 |
| **요약은 Anthropic 전용**(가진 키), OpenAI/Gemini 금지 | `OPENAI_API_KEY not set` 류 실패 방지 |
| 실패 반환에 `message`(실제 사유) 포함 필수 | 원인 추적 가능 |
| 도구 최대 4개(fetch/summarize/email/schedule 각 1개) | 중복·거대 페이로드 방지 |
| Evaluator가 위 위반을 **오류로 판정** → 재생성 유도 | 규칙 강제 |

### (2) 생성 단계 결정적 보정 — Provisioner 노드 (`nodes/provisioner.py`)

- `_dedupe_tools_by_stage()`: LLM이 규칙을 어겨도 **단계별로 도구 1개만 남기고
  중복 제거**(fetch/check/summarize/email/schedule). 예: 8개 → 4개.
- `_ensure_shared_fetch()`: **fetch 단계 누락/취약 시 공용 파서 기반 fetch 주입.**
- `_ensure_delivery()`: **발송이 필요한 요청인데 메일 도구가 빠지면 검증된 표준
  SMTP 도구를 결정적으로 주입.** 요청문에서 수신자 이메일을 정규식으로 추출한다.
  → Solo 모드(재생성 루프 없음)에서도 "메일 안 감" 누락을 원천 차단.

### (3) 런타임 방어 — 실행 시 (`services/tool_runtime.py`, `services/agent_runner.py`)

| 방어 | 설명 |
|------|------|
| **시그니처 기반 인자 바인딩** | 함수가 받는 인자만 전달, 없는 필수 인자는 `""`로 채움 |
| **인자는 stdin(JSON) 전달** | 명령행 길이 제한(ARG_MAX) 초과 → `Errno 7` 방지 |
| **전달 텍스트 50,000자 절단** | 원본 HTML이 흘러도 메모리 보호 |
| **LLM/SMTP 키 자동 주입** | `.env`의 `ANTHROPIC_API_KEY` 등을 도구 환경에 주입 |
| **구조화된 에러 보고** | 실패 시 `tool.py N번째 줄 / 에러타입 / 메시지 / 트레이스백` 표면화 |
| **실질 실패 진단** | status가 success여도 `blocked`/본문 없음/`error_message`면 실패로 판정 + 사유 노출 |

### (4) Dual 모드 자가개선 (Critic 모드 ON일 때만) {#self-heal}

생성 페이지에서 **"Critic 모드 (Dual Supervisor)" 체크 시** 동작한다.

```
builder(도구 생성 + dry-run 실제 실행) → critic(실행 결과로 평가)
        ↑                                          │
        └──── 런타임 실패 시 개선안 반영해 재생성 ──┘   (max_rounds=2)
```

- Builder가 생성 직후 **파이프라인을 dry-run으로 실제 실행**(`run_agent_pipeline(dry_run=True)`,
  메일 등 발송 계열은 건너뜀)해 `runtime_test`(성공/실패·사유·단계별 상태)를 만든다.
- Critic은 이 **실제 실행 결과**를 보고, 실패면 `passed=false`로 판정하고
  실패한 도구/단계를 겨냥한 개선안을 낸다 → consensus 미합의 → builder 재생성.
- **Solo 모드는 smoke test 없음**(빠른 1회 생성). 실행 검증·자가개선이 필요하면 Critic 모드를 켤 것.

### (5) 하네스(Harness) — LLM/도구 실패를 흡수하는 보호막 {#harness}

한 노드/도구의 일시적 실패가 **전체 생성·실행을 통째로 죽이지 않도록** 감싼다.
두 종류가 있다.

#### 5-A. 생성 단계 JSON 하네스 (`agents/meta_agent/harness.py`)

- 문제: provisioner가 만드는 JSON 안 `"code"` 필드에 **실제 줄바꿈/따옴표**가 들어가면
  기본 `json.loads`(strict)가 거부 → 노드가 예외를 던지고 orchestrator까지 전파되어
  **HTTP 500**으로 생성 전체가 실패했다.
- 1차 방어 — **파서 강화**(`core/llm/utils.py`): `json.loads(..., strict=False)` 로
  문자열 내부 제어문자(줄바꿈/탭) 허용. 코드펜스·잘린 JSON 복구와 함께 18개 노드에 즉시 적용.
- 2차 방어 — **재시도 래퍼** `ainvoke_json(llm, messages, node, retries, fallback)`:
  파싱 실패 시 *"깨진 출력 + 유효 JSON으로 다시 내놔"* 지시를 붙여 재시도하고,
  끝내 실패하면 **안전한 fallback** 을 반환(빈 결과는 Completer/Critic이 잡음).
- 적용 노드: requirements / planner / provisioner / evaluator / builder / critic / counter_review.

#### 5-B. 런타임 하네스 (`services/agent_runner.py`)

- 생성된 에이전트를 **실행할 때** `execute_tool` 을 `_execute_with_harness` 로 감싼다.
- **일시적 실패만 재시도**: 타임아웃·네트워크·DNS·502/503/504 등(`_is_transient_failure`).
- **코드 버그(NameError 등)는 재시도 안 함** — 같은 입력으로 반복해도 동일하므로.
- **발송/알림 도구는 재시도 안 함** — 메일 중복 발송 방지.

> 즉 생성 하네스(JSON 자가복구)와 실행 하네스(전이적 실패 자가복구)가 별개로 동작한다.

## 5.6 도구 청소부(Tool Janitor) — 삭제 시 무엇을 지울지 판단하는 심판 {#janitor}

에이전트를 삭제할 때 **전용 도구는 정리하되 공용/필수/공유 도구는 보존**한다.
`services/mcp/tool_janitor.py` 의 `judge_tool_deletions()` 가 2단계로 판단한다.

### (1) 하드 규칙 — 절대 삭제 금지

| 보호 대상 | 근거 |
|-----------|------|
| **공용 도구** (`shared_tools`: `universal_parser`, `site_parser` 등) | `_SHARED_DIR` 에 영구 보존, 모든 에이전트가 재사용 |
| **필수 도구** (`metadata.essential = true`) | 명시적으로 보존 표시된 도구 |
| **다른 에이전트가 참조 중인 도구** | 레지스트리 전체를 스캔해 `project_files.tools` 에서 사용 여부 확인 |

### (2) LLM 심판 (하네스로 감쌈)

- 하드 규칙으로 걸러지지 않은 **회색지대 도구**만 LLM 이 `delete`/`keep` 판단:
  - 이 에이전트 전용(맞춤 fetch/summarize/email) → **delete**
  - 범용·재사용 가능 유틸리티 → **keep**
  - 모호하면 → **delete**(에이전트가 사라지므로 잔여 정리 우선)
- 파싱 실패/타임아웃 시 fallback: 회색지대 전부 삭제(기존 정리 동작 유지).

### (3) 삭제 경로 (`api/meta_agent.py` `delete_agent`)

```
후보 수집(project_files 매칭 + prefix 매칭, 공용 제외)
  → judge_tool_deletions() 로 delete/protected/kept 분류
  → delete 목록만 실제 삭제, prefix 정리도 keep 집합은 건너뜀
  → 응답에 protected_tools / kept_tools 포함
```

- 프론트(`AgentDashboardPage`)는 삭제 후 **"삭제 N개 / 보호 / 보존"** 내역을 알림으로 표시.
- `delete_tools_for_agent(agent_id, keep=...)` 에 보호 집합을 넘겨 prefix 정리에서도 제외.

## 7. 동작 가능한 E2E 플로우

### 문서 → 검색 (동작)

```
업로드 → 전처리 → 임베딩(embed API) → Milvus → /api/search/query → rerank → 결과
```

### Meta-Agent 에이전트 생성 → 실행 → 메일 (동작)

```
POST /api/meta-agent/create
  → Registry 조회 (HIT이면 재사용)
  → MISS: Solo(1회) 또는 Dual(Builder↔Critic, max_rounds=2)
  → Provisioner가 실행 가능한 도구(.py) 생성·저장 → 등록

POST /api/meta-agent/registry/{id}/run  (또는 스케줄)
  → prereq 통과 시 도구 파이프라인 실행
  → fetch → summarize → send_email → 수신함 도착
```
